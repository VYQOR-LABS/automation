1. Important service and access notice

Vico AI is configured as a single-owner service. It connects to one shared Google account and uses a shared application-owner context. It is not currently designed to isolate Google Calendar, Gmail, or assistant data between individual people who can reach the deployment.

The application does not currently implement HTTP authentication for its general API routes. Depending on how it is deployed, a person who can reach those routes may be able to request or trigger access to the shared account. WhatsApp senders may also share the same owner context; a valid WhatsApp platform signature confirms the platform sent a webhook, not that the sender is the account owner. The operator must restrict the service to trusted users and networks or put an appropriate authentication and authorization layer in front of it. Do not expose an unprotected deployment to the public internet.

Only connect a Google account whose owner has authority to grant the requested access and understands that the integration is shared by this deployment.

2. Information we handle

The information handled depends on which integrations and features the operator enables and what people send to the service. It may include:

  • Messages and contact details: message text, sender phone number, delivery or platform identifiers, and information included in a WhatsApp message or API request.
  • Google account data: Calendar event details and Gmail message data retrieved in response to a request. Gmail search can return message identifiers, subject, sender, recipient, date, snippet, and message body text depending on the operation.
  • AI request data: the message being processed, relevant context returned by enabled features, and results from Calendar or Gmail tools used to answer the request.
  • Account and integration data: internal owner identifiers, integration status, granted Google scopes, and encrypted Google access and refresh tokens.
  • Action and approval data: the details needed to evaluate, approve, reject, or record certain Calendar and email actions, along with their status and audit metadata.
  • Technical and diagnostic data: request method and route, request timing, network address metadata, operation names, response status, error details, and service logs needed to operate and troubleshoot the application.

Please do not send passwords, payment-card security codes, authentication secrets, or other information that is not needed for the requested task.

3. Google user data: access, use, storage, and sharing

This section specifically describes Google user data handled by Vico AI. Vico AI connects one shared Google account for this application deployment. Google data is accessed only after the account owner completes OAuth consent, and is used to carry out the requested Calendar or Gmail feature and, where requested, to generate an answer from the retrieved information.

Data accessed and why

The OAuth consent request contains these scopes. The scope authorizes access; whether a particular operation is available also depends on the application workflow:

  • Calendar: the https://www.googleapis.com/auth/calendar.events scope allows viewing and managing events on the connected account's calendars. The current application lookup reads event identifiers, titles, descriptions, start/end times, locations, and status from the primary calendar. The service layer also implements event creation, retrieval, update, and deletion; the general HTTP API currently exposes event lookup, while other operations depend on configured tool workflows.
  • Gmail: the https://www.googleapis.com/auth/gmail.readonly scope allows finding and reading Gmail messages. The service may access message IDs, thread IDs, snippets, dates, sender/recipient/subject headers, and available message body text. Search terms are sent to Gmail as the message query. The https://www.googleapis.com/auth/gmail.send scope permits sending email. The service layer can send the recipient addresses, subject, and body supplied for an email action; the configured application workflow determines whether this function is available to a user.

How Google data is used

  • Calendar event data is returned to the user or included in an assistant response when the user asks Vico AI to look up relevant events.
  • Gmail search results and, when requested, message content are used to answer a Gmail-related request. The AI assistant may receive relevant Gmail results together with the user's request to generate the answer.
  • Email and Calendar write operations, when made available by the configured workflow, are performed only to carry out the requested action. Certain sensitive email and Calendar changes are subject to the application's approval workflow.
  • OAuth credentials are used to authenticate requests to Google and refresh access when needed.

Vico AI does not use Google user data for advertising, sell it, or use it to create advertising profiles. It is not used for a purpose unrelated to providing or improving the application's user-facing features, security, compliance with law, or a purpose the account owner has expressly authorized.

Storage and protection

Access and refresh tokens, token expiry, token type, granted scopes, and integration metadata are stored in the operator-configured PostgreSQL database. The access and refresh tokens are encrypted before storage using AES-256-GCM and an operator-configured base64-encoded 32-byte encryption key. Tokens are decrypted in application memory when needed; the Google client library uses the access token to authenticate API requests. Expiring access tokens are refreshed and updated credentials are saved. The OAuth callback does not return tokens. The encryption key is separate from the token database and must be restricted and protected by the operator. Encryption of tokens does not mean that Calendar or Gmail content, or all other personal information, is encrypted at rest.

Calendar and Gmail results are used in the active request and can be returned in an API response or passed to the configured AI provider. The Google token store does not store message bodies or Calendar event results. When OpenAI is configured, generated responses are held in an in-memory application cache for up to 60 seconds; this cache is not a permanent database record. Ollama configuration does not add an application-level response cache. This repository does not establish a general retention period for data handled by the hosting, database, queue, AI provider, or backups.

Sharing and transfers of Google user data

  • Google: the OAuth authorization code, refresh requests, Gmail searches/messages, and Calendar requests are sent to Google to authorize and provide the requested integration.
  • AI provider: if the request uses Google results to generate an answer, the request and relevant tool results may be sent to the AI provider selected by the operator (OpenAI or Ollama). Ollama may run on the operator's machine or at a configured remote service. This transfer is for generating the requested user-facing response, not for advertising or an unrelated purpose. The provider's processing and retention depend on the provider and deployment; this repository does not establish their retention or model-training settings.
  • Infrastructure: encrypted credentials and operational data are processed by the operator-configured database, application host, queue, and logging systems. The application currently has no built-in HTTP authentication for general API routes. The operator must restrict access to the deployment and its infrastructure; the OAuth state cookie protects the OAuth callback but does not authenticate API users.

Application logs normally record Google operation names, status, duration, and result counts rather than event or message bodies. On a Google API failure, the logged request URL is sanitized to remove query parameters and fragments so that Gmail search terms are not included. Other operator infrastructure and provider logs are governed by their own configurations.

Google user data is not sold, used for advertising, or transferred to third parties for advertising. It is shared with a provider only as necessary to provide or improve the user-facing feature, to protect security, to comply with law, or with the account owner's consent. The operator must ensure any handling of Google user data by personnel or service providers complies with the Google API Services User Data Policy and its Limited Use requirements. This application does not implement human review of Google data as a product feature; any operational access must be limited to circumstances permitted by that policy.

Retention, revocation, and deletion of Google data

The application keeps the encrypted OAuth credentials in its database so the connected account can be used until credentials are replaced or removed by the operator. The code does not define an automatic deletion period for Google tokens or general database records, and it does not currently provide a self-service Google disconnect or data-deletion route. Google results are handled for the active request; copies held by an AI provider, infrastructure provider, logs, or backups are subject to those providers' and the operator's actual settings, which are not determined by this repository.

To stop future access, remove Vico AI from the connected account's third-party connections in Google Account security settings. Revoking Google permission may stop integration features but does not delete tokens or other data already held by the service operator. To request access, correction, or deletion of application-held information, contact kimaniwilfred95@gmail.com. The operator will review the request under applicable law and explain any limits on locating or removing data from active systems, logs, or backups.

Google API Services User Data Policy

Our use and transfer of information received from Google APIs will comply with the Google API Services User Data Policy, including its Limited Use requirements. In particular, Vico AI will not use or transfer Google user data for serving advertisements, including retargeting, personalized, or interest-based advertising; will not allow humans to read the data except with the account owner's affirmative agreement, when necessary for security purposes, to comply with applicable law, or for internal operations permitted by the policy using aggregated and anonymized data; and will not use or transfer the data to create, train, or improve a generalized AI or machine-learning model. Any transfer to an AI provider described above is limited to generating the response requested by the user and must comply with the policy's Limited Use restrictions.

We may use information to:

  • generate an assistant response using the AI provider selected by the operator;
  • send messages or perform supported Calendar and email actions when requested and permitted;
  • apply configured approval checks to higher-risk actions, such as changing or deleting a Calendar event or sending sensitive email;

  • meet legal obligations and respond to valid legal requests.

AI-generated responses can be inaccurate or incomplete. A response is not professional legal, medical, financial, or other regulated advice. Review information and proposed actions before relying on them.

5. How information is shared

Information may be processed by the following services when needed to provide the requested feature:

  • Google: OAuth token exchange and refresh requests go to Google. Calendar and Gmail requests are sent to the Google APIs using the connected account’s authorization.
  • WhatsApp/Meta: when the WhatsApp integration is enabled, message content and delivery information are exchanged with the WhatsApp Business Platform and Meta Graph API.
  • The configured AI provider: the assistant sends the current request and, where relevant, selected context and tool results to the provider selected by the operator. The available choices include OpenAI and Ollama. Ollama may run locally or at an operator-configured remote address; a remote Ollama deployment can be operated by a separate organization. The provider’s own privacy terms and configuration govern its processing.
  • Service infrastructure: for the Render deployment, Render hosts the application. The configured PostgreSQL database, Redis-backed queue infrastructure, and logging systems may also process information needed to run the service. This repository does not identify the database and Redis providers or their data locations.

This application has no feature for selling personal information. The repository does not establish other operator-level business data practices. Google API data is not disclosed to an AI provider for advertising. Where a user asks the assistant to answer using retrieved Google information, relevant request context and tool results may be included in the AI-provider request so it can produce a response. Check the selected provider and its data terms before using the service with sensitive information.

Information may also be disclosed where required by law, to protect the rights and safety of people or the service, or as part of a business reorganization with appropriate safeguards.

6. Retention and deletion

Information is kept for as long as it is needed to operate the service, maintain the connected integration, complete or audit an action, resolve disputes, comply with law, or protect the service. Actual retention periods depend on the operator’s database, log, hosting, and backup configuration.

The application does not currently provide a self-service account deletion or Google disconnect endpoint, and the code does not establish a general automatic deletion schedule for stored records. Do not assume that deleting a message, revoking Google access, or disconnecting a platform automatically deletes information already stored in the application database, logs, or backups. Pending approvals expire after the configured approval interval (10 minutes by default); this does not mean all associated records are deleted.

To disconnect Google, open your Google Account's third-party connections or security settings and revoke Vico AI's access. The application currently has no self-service disconnect route. Revoking access in Google stops future API access after the revocation takes effect, but it does not by itself erase tokens or other data already held by the service operator. Contact the privacy email below to request access, correction, or deletion of stored information. The operator must assess requests under applicable law and its ability to identify and remove data from active systems, logs, and backups; no automatic deletion guarantee is made here.

7. Security

The application encrypts Google OAuth tokens at rest in the database using AES-256-GCM with an operator-managed key, and uses a state value protected by a short-lived HttpOnly cookie to protect the OAuth callback. This is not a claim that all personal information is encrypted at rest. Diagnostic logs record request and operation metadata; responses from some routes may also be logged. Access to logs, databases, backups, application hosts, and encryption keys must be restricted and monitored by the operator.

No method of storage or transmission is completely secure. The application currently lacks built-in authentication for general HTTP API endpoints, so access restrictions at the network or deployment boundary are essential. Do not treat OAuth state protection as API authentication.
