The platform

One assistant. Connected capabilities.

Vico AI is designed around an orchestration layer: incoming requests are interpreted, relevant tools are selected, and results are assembled into a response. Integrations operate only within the permissions and configuration available to the application.

Implemented

WhatsApp messaging

Processes configured WhatsApp Business Platform webhooks and supports outbound text and template messages, plus message-template and phone-number management. Meta account setup, permissions and eligibility apply.

Implemented

Google Calendar

After the connected account owner authorizes Google, the backend can look up events in the account's primary Calendar. The OAuth request also includes permission to manage events; actual event changes depend on the configured workflow.

Implemented

Gmail integration

The service layer supports Gmail message search and retrieval, with email sending implemented in the backend. User-facing availability depends on the deployed application workflow.

Configuration-dependent

Permission-aware access

Google requests require an account owner's OAuth consent. WhatsApp webhook signatures are checked for platform-originated requests. These controls serve different purposes and are not interchangeable.

Implemented

AI orchestration

The backend can use its configured AI provider to interpret requests and prepare responses. Depending on deployment configuration, the provider may be a hosted AI service or a locally operated model.

Operator-managed

Application context

The current deployment uses a shared application-owner context and a shared connected Google account. It is not currently a self-service, multi-tenant product with separate accounts for every end user.

Google connection

Google access starts with account-owner consent.

Vico AI uses Google's OAuth authorization flow for the connected application-owner account. The account owner approves the requested scopes before the backend can make authorized Google API requests.

Illustrative Google OAuth lifecycle

Authorization is granted by a Google account owner—not by the AI model.

OAuth 2.0
STEP 01 Owner starts connection

The application creates an authorization URL and state value.

STEP 02 Google consent

The owner signs in and approves the requested Gmail and Calendar scopes.

STEP 03 Secure callback

Google returns an authorization code; the backend validates state and exchanges the code.

STEP 04 Token storage

OAuth credentials are encrypted and stored in the configured database.

STEP 05 Authorized API calls

The backend uses the stored authorization to access permitted Google services.

Access is limited by the scopes granted, Google's policies, token validity and the application's configured workflows. The account owner can revoke access through their Google Account settings.

Data and permissions

Connected services have distinct trust boundaries.

Each integration has its own authentication and authorization mechanism. A message arriving through one channel does not automatically grant access to data held by another connected service.

Google account data

Google features require OAuth consent from the account owner. The current authorization request includes:

  • Google Calendar event access.
  • Gmail read access.
  • Gmail send access.

OAuth tokens are encrypted before being stored in the configured database. Google API requests remain subject to the granted scopes and Google's own authorization controls.

WhatsApp messages

WhatsApp integration requires configured Meta Business Platform credentials, phone-number identifiers and webhook configuration.

  • Webhook signatures help verify requests from Meta.
  • Outbound messaging depends on the configured WhatsApp account and platform rules.
  • A sender's WhatsApp message does not itself authorize access to the connected Google account.
Transparency

What the current deployment does—and does not—provide.

We aim to describe the current backend accurately. The availability of a capability in service code does not necessarily mean it is exposed as a user-facing feature in every deployment.

Deployment and access notice: The current application uses a shared owner context and does not provide built-in general HTTP authentication or per-user isolation for all API routes. The operator must enforce appropriate network or upstream access controls before exposing protected API functionality to the public internet.

Current limitations

  • Separate end-user accounts and per-user Google data isolation are not currently available.
  • A self-service Google disconnect and data-deletion interface is not currently implemented.
  • General HTTP API authentication is not implemented by the application itself; deployment-level controls are required.
  • Calendar event changes and Gmail sending exist in backend service code, but are not exposed as general user-facing API routes in the current backend.

What this means

  • The service is currently operator-managed rather than an open public sign-up product.
  • Connected accounts should belong to, or be authorized by, the account owner.
  • Do not use the service for workflows requiring account isolation or controls that the operator has not configured.
  • This page describes the implementation currently present in the application, not a feature roadmap.
